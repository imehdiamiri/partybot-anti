# PartyBot performance and security benchmark — 2026-09-30

## Decision

The defined **100- and 1,000-client local multiplayer workloads completed without
operation errors**, and every client received every tested state version. This is
encouraging, but **does not certify 1,000 real production users or crash-free mobile
operation**. Production received only 22 bounded, read-only Hosting requests and
read-only infrastructure metadata checks. No customer data, purchases, advertisements,
accounts, billing settings or deployed application code were changed.

Source under test: `1699b17e6c69277fb41f0431cdd843c980f5a2e9`.
Raw reviewed measurements: [2026-09-30-results.json](2026-09-30-results.json).
Times in that file are UTC September 29; local test date is September 30 in Istanbul.

## Workload and limits

- Local RTDB emulator 4.11.2, Firestore emulator 1.22.0, Java 26, Node 22.16.0;
  Windows desktop, i9-10900K, 20 logical processors, 31.9 GiB RAM.
- Distinct rules-test authenticated SDK clients, 4 players per room: 25 / 250 rooms.
  Actual `.info/connected` acknowledgements verified for all 100 / 1,000 clients.
- Connection ramp in bounded groups. Three listeners per client (whole room,
  game state, presence); these represent the app's subscription shapes, not a
  mounted React application. Host action collection uses reads at each wave.
- Six synchronized waves over 30 seconds per scenario: presence every 5 seconds;
  each guest submits an action every 10 seconds; each host verifies 3 queued
  actions, writes each watermark and removes each action separately, then
  broadcasts a state with approximately 1 KiB of turn data every wave.
- This intentionally stresses simultaneous bursts. It is not an arrival-rate
  capacity search, long soak, fast-tapping game, or full user journey. Authentication
  is synthetic; Auth providers, Cloud Functions scaling, Firestore load, RevenueCat,
  ads, recording/audio, real device memory, frame rate and internet RTT are excluded.
- Latencies below are successful SDK operation acknowledgements, not rendered
  user-perceived latency. Recipient checks confirm delivery, but do not time it.
  Host drain latency covers three actions and their six sequential writes.
- Initial attempt aborted during a 100-client join with emulator `INTERNAL_ERROR`.
  Its cause was not established; it must not be called an app crash or concealed.
  A subsequent preliminary run with batched acknowledgements passed. The final
  reported run uses the app's separate acknowledgement writes. This is not evidence
  of long-term stability from repeated production runs.

Operation groups include a compound drain; they are **not raw database writes**.
The final workload performs 1,425 / 14,250 steady-state writes (47.5 / 475 per second
on average), excluding setup. Bursts are much higher. Snapshot bytes are repeated
application-level JSON serializations, **not billed wire traffic**, because the SDK
can transfer deltas. RSS is the load generator, not an individual phone or server.

## Live site and cloud observations

- https://partybot.games: 22/22 HTTP 200 responses, concurrency <= 2. First homepage
  fetch 1,630 ms including connection setup; ten subsequent homepage fetches median
  91.5 ms, nearest-rank p95 246.1 ms. Small sample from one location, no SLA claim.
- Main entry bundle: **10,566,810 bytes decoded; 1,483,912 bytes Brotli**. Fetch took
  386 ms here. Parse/evaluation and first interactive paint were not measured.
  This is a material startup concern on low-end devices despite CDN compression.
- Immutable one-year bundle caching and HSTS observed. HTML is no-store. CSP,
  X-Content-Type-Options and X-Frame-Options were absent on probed responses.
- Google Cloud billing API confirmed `billingEnabled: true`. All 12 listed v2
  functions ACTIVE: 256 MiB, 1 CPU, concurrency 80, maximum 20 instances, minimum 0.
  These settings do not prove available quota, cold-start performance, throughput
  or ability to sustain 1,600 concurrent requests. Costs/budget alerts were not audited.
- Firebase documents 100 simultaneous RTDB connections on Spark, 200,000 on Blaze,
  and approximately 1,000 writes/sec per database. Billing is enabled here, so a
  Spark-only 100-connection ceiling is not the expected constraint. User count alone
  remains an inadequate capacity measure: 1,000 users can approach write limits in
  a fast game even though a slow game fits this synthetic average.
  Sources: [RTDB limits](https://firebase.google.com/docs/database/usage/limits),
  [optimization](https://firebase.google.com/docs/database/usage/optimize).

## Security results and prioritized findings

Existing app tests: **45 suites / 323 tests PASS**. Backend/RTDB/Firestore:
**2 suites / 75 tests PASS**. During both workloads, anonymous room reads, outsider
room reads, guest state replacement, wallet forgery and forged player actions were
denied. These are tests of repository rules on emulators, not a comparison against
the exact currently deployed rules or a full penetration test.

1. **P1 — Payload limits are incomplete (confirmed locally).**
   `database.rules.json` documents at most 200 turn-data children but does not enforce
   that count. A host wrote 201 children successfully. A nested 17,000-character
   string also bypassed the direct-child 4,096-character constraint. Hosts already
   own their room; this demonstrates resource-abuse protection gaps, not access to
   another user's private data. Define and enforce compatible bounded schemas for
   each game before widening production traffic; test existing game payloads first.
2. **P1 — Abuse protection needs an explicit rollout.** No App Check enforcement
   was found in the reviewed callable definitions/client source. Per-user callable
   rate limits exist, but direct RTDB room/actions/telemetry writes have no aggregate
   rate limiter. Authenticated automated traffic can drive costs. Configure attestation
   and monitoring with web/native/Expo Go compatibility in mind before enforcement.
3. **P2 — Whole-room listeners amplify client work.**
   `MultiplayerService.listenToRoom` subscribes to the room root while state and
   presence have separate subscriptions. Every action/presence change can trigger
   another large room snapshot callback. Narrow subscriptions and profile devices;
   the 95.57 MB snapshot tally is evidence of callback work, not network billing.
4. **P2 — Unbounded room scans.** The scheduled sweeper and account deletion read
   the entire rooms tree (`functions/index.js`). Indexed activity metadata and
   bounded pagination should replace full payload scans at larger scale.
5. **P2 — Startup bundle and browser headers.** Split heavyweight game/audio/data
   modules and measure mobile Web Vitals. Add compatible security headers with an
   explicit audit of Google login, ads and other embeds; do not blindly deploy a
   restrictive CSP that breaks these flows.
6. **Dependency audit:** `npm audit --omit=dev` returned **0 critical / 0 high**,
   but **15 moderate** backend and **49 moderate** Expo dependency entries. These
   counts include transitive/toolchain paths and are not 64 distinct remotely
   exploitable application bugs. Triage advisory reachability; no forced upgrades
   or native runtime changes were made for this benchmark.

Separately, the previous GitHub incident's legacy RevenueCat key revocation remains
unverified in this review; clean Git history does not establish revocation.

## Release recommendation

Proceed with a monitored small beta; do not advertise certified 1,000-user capacity
from this run. Before broad release: resolve the payload/abuse controls, reduce
subscription/bundle overhead, then run a 15–30 minute staged-cloud soak with the
production rules/region and representative game mix at 100 -> 500 -> 1,000 users.
Measure backend p95/p99, queueing, database load/egress, error rate, costs, and real
iOS/Android/web frame/memory behavior, including reconnect/host migration. Agree a
request and spending ceiling before that cloud load test. This report neither
changes store readiness nor certifies authentication, ads or payments under load.

## Reproduction

From the repository root with existing dependencies, Java and Firebase CLI:

```sh
npx --yes firebase-tools emulators:exec --only database,firestore --config firebase.security.json --project demo-partybot-benchmark "node functions/benchmark-suite.cjs"
node scripts/benchmark-live.cjs
```

The first command is emulator-only and rejects non-loopback database targets.
The second makes at most 22 read-only requests to the fixed live origin. Do not turn
it into a high-concurrency production test. Raw output is written to ignored
`.security/benchmark-*.json`; reviewed snapshots are saved beside this report.
`--checks-only` on the suite runs payload probes and regressions without repeating
the load. Payload probes deliberately report acceptance as findings, not passing
security guarantees. The load harness fails fast, has a ten-minute deadline, and
records completion/failure status for future runs.

On this Windows/Java setup the CLI reported shutdown but left its Java children
alive. Their exact command lines and creation times were checked, then only those
test processes were stopped. No persistent app server was started. A Jest config
discovery issue in the first combined runner was corrected; the subsequent 75-test
run passed. No app/deployment changes were made or claimed.
